# Invasion v2 — operational rollout

**Not enabled by Phase 7.** Do not run these activation commands until an operator approves a test group and verifies the actual production DB flag, backups, migrations, assets, bot token, seeded regions, and authoritative group membership/Main Cards. Source defaults cannot prove the live flag value.

## Prerequisites and preparation

1. Back up the DB and verify the Alembic chain includes `036_invasion_v2`, `037_inv2_group_members`, `038_inv2_admin_logs`, **`039_archive_inv1_tables`**. Apply migrations 036–039 in order. Migration 039 renames five V1 tables to `_archive_inv1_*` and adds nullable `inv2_invasions.delivered_at`; it never drops a table. Check row counts and archived foreign keys before and after migration. Its downgrade renames back and removes `delivered_at`; do this only after disabling the flag and rolling back app code that reads that column. Preserve the backup.
2. Verify ten V2 regions exist, the Group is active, its members are observed by the membership hook/backfill, and **every** currently active member has a valid Main Card. Check that the registered DB power resolver returns a positive average; it fails closed if anyone lacks a card or the membership/power record is uncertain. Ensure local image font/artwork is present. Use private admin chat only; `/inv2_health` and `/inv2_status` show the flag and process-local activity.
3. With the deployed flag **off**, inspect `/inv2_config`, `/inv2_regions`, `/inv2_health`. No V2 scheduler writes or group messages should happen while disabled. Run the isolated tests before any rollout; do not treat a local test-DB flag as deployment authorization.

## One-group trial (operator actions, not executed here)

1. For an approved test group and a monitored window, send **`/inv2_toggle on`** in a private admin chat. This is a future operator instruction, **not** an action performed in Phase 7. Wait for cache invalidation (cross-worker caches may retain their old value for up to 60 seconds). Only one group is scheduled per global interval; eligibility requires an active/unmuted group, resolver power and seeded regions.
2. The first eligible maintenance tick creates a DB-only **PENDING** row. A separate post-commit publisher sends the photo/caption with an `inv2:join:<id>` button and turns it **ACTIVE only after successful delivery**. There is no promise of an immediate spawn: the global interval, round-robin group selection, active battles, mute, or unresolved Main Cards can defer it. To request a manual test row for an eligible group, use `/inv2_force_spawn <group_id> [region_code] [enemy_type]` in private chat; it bypasses only the interval and still needs the enabled flag. Monitor group messages rather than sending a real one from tests.
3. Inspect `/inv2_health`, `/inv2_invasions`, `/inv2_group_info <group_id>`, the `inv2_tick` log record and `inv2 recovery: {...}` startup log. The health fields are process-local (`last_tick_at`, duration, `last_error_at`, message); check each worker separately. `inv2_tick` carries `spawned`, `finalized`, `expired`, `skipped_muted`, `skipped_active`, `skipped_no_resolver`, and `duration_ms` in Python logging `extra` fields; the default console formatter displays only `inv2_tick`, so use a structured log sink to index the fields.
4. Keep this trial limited to **one test group for 24 hours**, reviewing sends, state transitions, reward rows/items, muted groups, and reconciliation warnings. Expand only after an operator reviews observed outcomes and approves additional groups. There is no group-scoped enable flag; control scope operationally through active/muted Group state and timing, not by assuming the global toggle affects one group.

## Fast disable / rollback

Use **`/inv2_toggle off`** in private admin chat immediately on unexpected behavior. Confirm disabled via `/inv2_health`, accounting for per-worker cache TTL. The on-call operator can `/inv2_mute <group_id> <hours>` or `/inv2_unmute <group_id>` as appropriate; breaker mute defaults to 24 hours. With the flag off, normal V2 tick/presentation/recovery sends are gated. If a code/schema rollback is necessary, stop workers, take another backup, check the archived data, then downgrade **039** to rename all V1 tables back; never drop the archives. Reversing 039 also removes `delivered_at`, so use code compatible with the downgraded schema. Do not downgrade historical 031 just to recover old data.

## Known limitations and crash safety

- Telegram messages and database commits are **not atomic**. A successful final photo before its `delivered_at` stamp commits may be resent after a crash. Startup recovery retries only undelivered VICTORY photos, checks the group circuit breaker, leaves failed sends NULL for a later startup, and never grants rewards. It expires overdue ACTIVE rows without rewards or messages.
- Reconciliation warns if reward rows lack matching attacks or group victory/defeat counters differ from terminal invasion counts. It does **not** repair them; investigate before rollout. Defeat final-photo recovery is not included. An unannounced PENDING row is retried by maintenance, not by startup victory recovery.
- A TelegramBadRequest/forbidden send is counted by the breaker; its mute is 24 hours by default, and an admin can unmute. A resolver with an unknown member's Main Card **fails closed** rather than substituting an estimate.
- `/inv2_simulate` is game-state read-only but writes **one mandatory admin audit row**. Manual force-end settles DB state without sending a group result photo. The asset manifest under `assets/invasion/` describes V1 artwork provenance, not a live V2 loader.
- This phase did not inspect the deployed DB or change its live flag. The known six unrelated full-suite failures are documented in [the phase report](PHASE-7-REPORT.md); the isolated V2 suite is green.
