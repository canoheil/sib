# Phase 4.5 — Group Power Resolver implementation

## Delivery

- **Revision:** `037_inv2_group_members`, after `036_invasion_v2`; adds only `inv2_group_members` and inserts `inv2_member_active_window_days = 30` if missing. Schema downgrade removes its table/indexes. It deliberately retains the config key because a pre-existing/customized row cannot be distinguished from a seeded row on downgrade. `system_config` has no description column; the requested description (“Days after which a group member is considered inactive.”) is documented in the migration, code, and design spec instead of altering an existing table.
- **Model:** `database/models/invasion_v2_group_member.py`, exported by `database/models/__init__.py`. BIGINT auto-ID (INTEGER variant only in isolated SQLite tests), FKs/indexes for user and group, unique `(user_id, group_id)`, composite `(group_id, last_seen_at)`, non-null activity/creation/update timestamps.
- **Hook:** `bot.py:29–33` installs the same `GroupMembershipMiddleware` as outer middleware for messages and callbacks *before* rate limiting. `middleware/group_membership.py:55–75` extracts only real users in group/supergroup chats; `:86–113` throttles once per pair/60s, bounds pending writes at 256, and schedules a task with `asyncio.create_task` **without awaiting a database call in the handler**. `:25–45` inserts/atomically advances only `last_seen_at` on duplicate (MySQL/MariaDB + SQLite test dialect); DB errors are swallowed at DEBUG by `:77–84` and remove the throttle entry to permit retry. Other handler behavior is unchanged. Sub-millisecond enqueue is a design target, not a verified production latency SLA.
- **Resolver:** `services/invasion_v2/power_resolver_impl.py`, `DbGroupPowerResolver.average_main_card_power(*, group_id, session)`; registered before recovery in `bot.py:53–58`, logging `inv2 power resolver: DbGroupPowerResolver`. It reads every member observed within the configurable 30-day window, uses the existing `PlayerCardService.get_main_card` selection and `card_attributes(card, character).power` computation, and averages only if **every** active member has a valid Main Card and certain attributes. No rows, missing card/character, invalid window/power/level or query error → `None`, no guessed fallback. Existing `invasion_enabled` gates in maintenance/recovery/scheduler remain unchanged; resolver registration does not enable the feature.
- **Backfill:** `scripts/backfill_inv2_group_members.py` reads direct `match_players` user/group associations (excluding bots), chooses the latest `created_at`/`updated_at` per pair, and only inserts or advances activity. It does not date old players as newly active. The script prints target URL without credentials, requires an exact `--confirm-database NAME` for writes, supports `--dry-run`, and exits cleanly if the source table is absent. Run from the repository parent: `python -m sib.scripts.backfill_inv2_group_members --dry-run` after a reviewed migration; actual writes require explicit confirmation. No startup backfill.
- **Files:** `database/migrations/versions/037_inv2_group_members.py`, `database/models/invasion_v2_group_member.py`, `database/models/__init__.py`, `middleware/group_membership.py`, `bot.py`, `services/invasion_v2/{power_resolver_impl,power_resolver,scheduler}.py`, `services/config_store.py`, `scripts/backfill_inv2_group_members.py`, `tests/invasion_v2/{test_group_power_membership,test_group_member_migration}.py`, `docs/invasion-rework/{PHASE-1-DESIGN,PHASE-4.5-REPORT}.md`.

## Limits / remaining work

- Telegram offers no complete member roster in this hook. Only users whose group updates the bot sees (plus credible historical match rows) are counted; silent members are unknown. A known active user without a valid Main Card blocks a spawn rather than being dropped from the average. FK writes may initially fail for a group/user not registered by existing handlers; the hook logs DEBUG and retries on future activity. Throttling/backlog cap intentionally lose intermediate observations, not user messages.
- Historical backfill source may omit users who never played a match, and its older timestamps can be outside the 30-day window. The script uses in-memory aggregated pairs/observations; review memory requirements before very large backfills. MySQL/MariaDB statements were compiled but not exercised against a live DB.
- Phase 5 still needs announcement/delivery/activation; installing the resolver does not cause sends or enable invasions. Earlier unresolved design questions about join/attack and region mapping are not decided by Phase 4.5.
