### Archive / ORM choice

039 **renames rather than drops** `invasions`, `invasion_waves`, `invasion_contributions`, `invasion_defense_actions`, `invasion_participants` to `_archive_inv1_invasions`, `_archive_inv1_waves`, `_archive_inv1_contributions`, `_archive_inv1_defense_actions`, `_archive_inv1_participants`. The migration re-inspects each table so a partial MariaDB DDL run can safely be retried; it refuses ambiguous simultaneous old+archived tables. Downgrade renames them back and removes the added nullable V2 `delivered_at` column. SQLite migration tests verify rows and foreign-key targets survive repeated upgrade/downgrade. Production MariaDB FK/index behavior and actual row counts require an operational dry run on a copy before rollout; do not assume SQLite proves them.

**Model decision:** remove the three V1 ORM files and their `database/models/__init__.py`/`database/__init__.py` exports rather than repoint mappings at archived names. This prevents `Base.metadata.create_all` from recreating writable old tables or treating archives as a live domain. Historical SQL migration 031 is preserved and independently tested. Archived rows remain readable through explicit SQL when authorized. The balance script is historical and not runnable after V1 module deletion; its published report/CSV remain intact. `assets/invasion/manifest.json` is historical provenance metadata: its `loaded_by` V1 paths are deliberately not executable configuration and are not rewritten to point at V2.

### Recovery dry run, logging and risks

In isolated SQLite with a mocked bot, recovery produced `{'expired': 1, 'delivered': 1, 'delivery_failed': 0, 'reward_mismatches': 0, 'group_mismatches': 0, 'disabled': False}`; repeating it yielded `expired=0, delivered=0`, with unchanged reward count. A separate injected TelegramBadRequest left `delivered_at` NULL and recorded the breaker failure; inconsistent reward/attack and group counters each produced a WARNING and were **not** repaired, then a successful retry delivered the photo. No real DB dry run was attempted.

Sample console line: `2026-10-14 09:40:00 [INFO] [sib] inv2_tick`. Its logging record includes `spawned=0, finalized=0, expired=0, skipped_muted=0, skipped_active=0, skipped_no_resolver=0, duration_ms=<nonnegative integer>` as `extra`; the default console formatter does not print these fields. `/inv2_health` exposes the process-local last tick time/duration and last error time/message. `inv2 recovery: {...}` is logged once per gated startup recovery call.

**Known limitations / before test-group activation:** live flag value and schema/archived row counts unverified; MariaDB FK rename and idempotent retry should be rehearsed; Telegram photo and `delivered_at` commit are non-atomic (crash can duplicate a photo); only undelivered VICTORY photos are replayed, not DEFEAT; recovery warnings are diagnostic, not repairs. Startup constructs the bot before recovery so delivery is possible; the flag guard still prevents sends while disabled. Multi-worker 60s cached flags and process-local health observations require operational review. A group resolver returns no power if any active member lacks a Main Card. The circuit breaker defaults to a 24h mute, and an admin can unmute. Simulation writes its required audit row. One test group for 24h is the proposed first trial, **not** automatically enabled here.
